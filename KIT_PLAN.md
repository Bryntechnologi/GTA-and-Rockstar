# Static Site Kit Extraction Plan

Working plan for extracting the reusable parts of FIVE STAR WANTED into a small Brynsites static-site
kit. This is intentionally **not** a general-purpose framework.

## Goal

Make the next Brynsites site start from the same reliable base:

- working local preview via `npm run dev`
- static pages generated from data
- shared header/footer and mobile navigation
- era/theme tokens with a contrast layer
- safe Markdown and wiki links
- share/reactions/reading progress
- search index generation
- sitemap, robots, llms.txt, and generated CSP headers
- CSP audit and browser tests

The site keeps its own content, data, copy, and visual identity.

## Recommended shape

Start as a local package inside a Brynsites workspace, not a public framework:

```text
packages/
  static-kit/
    src/
      chrome.mjs          # header, footer, breadcrumbs, nav config
      theme.css           # base tokens, era hooks, contrast layer
      markdown-core.js    # safe Markdown + [[wiki links]]
      engagement.js       # share, positive reactions, reading progress
      search.mjs          # index generation + browser search UI
      build.mjs           # page generation, sitemap, robots, llms, CSP hashes
      csp-audit.mjs       # enforced-policy audit
      dev-server.mjs      # local preview
    templates/
      page.mjs
      game-page.mjs
    tests/
    package.json
```

Site repos consume it through a workspace dependency or a local `file:` dependency until the API
settles.

## Config seam

Move site-specific values into one config object:

```js
{
  name: "FIVE STAR WANTED",
  url: "https://fivestarwanted.pages.dev/",
  umbrella: {
    name: "Brynsites",
    url: "https://brynsites.com/",
    contactUrl: "https://brynsites.com/contact"
  },
  nav: [
    { key: "games", label: "Games" },
    { key: "lore", label: "Lore" },
    { key: "story", label: "Story" }
  ],
  footer: {
    explore: [],
    project: [],
    elsewhere: []
  },
  archiveNote: "A partial, fan-made archive...",
  eras: {},
  pages: [],
  csp: {
    connect: [],
    media: []
  }
}
```

Content files stay in each site repo.

## Extraction phases

### Phase 1 — Freeze and seam

- Add config seams to the current build and chrome modules without changing output.
- Keep FIVE STAR WANTED as the reference implementation.
- Add a snapshot test that compares generated page structure before/after.

### Phase 2 — Move stable modules

Move these first because they are already isolated:

1. `markdown-core.js`
2. `engagement.js`
3. `dev-server.mjs`
4. `csp-audit.mjs`
5. `site-chrome.mjs`

Keep tests alongside each module. No visual changes.

### Phase 3 — Move build and theme

- Extract `build-static.mjs` into `build.mjs` with a config object.
- Split FIVE STAR WANTED-specific content renderers from generic page/sitemap/CSP output.
- Move theme tokens and the contrast layer into `theme.css`, leaving per-site era overrides in the
  site repo.

### Phase 4 — Prove it on a second site

- Build a second Brynsites site with the kit.
- Do not extract anything that only FIVE STAR WANTED uses.
- Fix the API based on actual friction, not guesses.

### Phase 5 — Version it

- Give the local package a version.
- Add a short README and migration notes.
- Decide whether to keep it private or publish it later.

## Non-goals

- CMS or backend.
- A universal component framework.
- A design system for every Brynsites property.
- Abstracting content models before a second site needs them.
- Replacing the current SPA or arcade.

## Success criteria

- A new site can run `npm run dev` and preview immediately.
- A new site can generate static pages, sitemap, robots, llms.txt, and CSP headers from config.
- Shared modules have tests independent of FIVE STAR WANTED content.
- FIVE STAR WANTED still passes its existing tests and Lighthouse checks.
- Extracting the kit does not make the current site harder to edit.

## Risks

- Premature abstraction: wait for the second consumer before generalizing.
- Theme coupling: keep base tokens generic and era palettes site-owned.
- Build coupling: keep content loaders separate from page rendering.
- CSP drift: hashes must be regenerated by the build whenever inline blocks change.

## Recommendation

Do not turn FIVE STAR WANTED into a framework. Finish it, build the next site, then extract the proven
parts into an internal static-site kit. The dev server and generated CSP work are already the first
pieces of that kit.
